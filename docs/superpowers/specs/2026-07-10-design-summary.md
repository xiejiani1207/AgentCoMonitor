# 跨智能体协同执行智能监控与结果筛选优化系统 — 设计方案

## 1. 项目背景与目标

多智能体协同任务已普及，但 Agent 执行日志、决策链路、异常行为、输出质量仍依赖人工 Review 校验。本项目构建一套**自动化智能监控与结果筛选优化平台**，实现"系统自动盯着 Agent 干活"。

**交付物**：原型系统 + 软件工程文档（需求、设计、开发、使用说明）

**场景策略**：监控平台领域无关；Demo 以金融投顾场景验证，保留通用扩展能力。

---

## 2. 系统组成

项目由两个相对独立的部分构成：

| | Part 1：通用监控平台 | Part 2：金融投顾 Demo |
|------|------|------|
| **定位** | 可复用的监控中间件 | 被监控的业务对象 |
| **核心内容** | Dashboard + 后端 + 4 大模块 + 适配器层 | LangGraph 6-Agent 链路 + Mock 数据 |
| **关键特征** | 框架无关，适配器模式对接不同框架 | 并行+串行混合拓扑 |

**关系**：Part 1 通过 LangGraph 适配器采集 Part 2 的执行数据；Part 1 不依赖 Part 2 的业务逻辑。

---

## 3. 系统架构

```
Web Dashboard (React)          — ECharts + AntV G6 + WebSocket
        │
FastAPI 后端                    — 监控采集 + 异常检测 + 质量评估 + 筛选优化
        │
框架适配器层                     — 通用 Trace 数据模型 + LangGraph 适配器
        │
Agent 执行层 (LangGraph)        — 6-Agent 投顾链路
        │
PostgreSQL                      — traces / anomaly_events / quality_scores
```

**技术栈**：Python + LangGraph + FastAPI + React/TypeScript + ECharts/AntV G6 + WebSocket + PostgreSQL

---

## 4. 四大核心模块

```
监控采集 → 异常检测 → 输出质量评估 → 结果筛选优化
 (发生什么?)   (哪里错了?)    (好不好?)      (选哪个?怎么改?)
```

### 4.1 执行监控
- 通过 LangGraph callbacks 机制注入监控钩子（on_chain_start / on_chain_end / on_chain_error）
- 采集每个 Agent 的执行时间、输入输出、token 用量、工具调用，生成标准化 TraceRecord
- WebSocket 实时推送至 Dashboard；通过 parent_trace_id 自动构建链路拓扑

### 4.2 异常检测（三层扫描）
| 层级 | 检测内容 | 实现 |
|------|----------|------|
| 执行层 | 超时、失败、重试、Token 飙升 | 规则引擎 |
| 行为层 | 循环调用、关键节点缺失、工具调用异常 | 链路分析器 |
| 输出层 | 格式不符、空输出、幻觉检测 | 内容校验 + LLM |

按高/中/低三级告警，高严重度触发 Dashboard 红色闪烁。

### 4.3 输出质量评估
五维度打分（0-100），加权计算综合分：

| 维度 | 权重 | 评估方式 |
|------|------|----------|
| 合规性 | 30% | 规则 + LLM 合规判断 |
| 准确性 | 25% | LLM 事实核查 |
| 完整性 | 20% | 检查点清单匹配 |
| 相关性 | 15% | 语义相似度 + LLM |
| 时效性 | 10% | 数据时间戳检查 |

**两层评估策略**：规则检查（< 50ms，第一层快速过滤）→ LLM-as-Judge（第二层语义评估）

### 4.4 结果筛选优化
- **筛选**：异常过滤 → 质量排序 → 多样性去重（相似度 > 95% 去重）→ 推荐 Top-3
- **优化建议**：双通道输出——人类可读建议（Dashboard 展示）+ Agent 结构化指令（self-correction）

## 5. 合规防线（跨 Part 1 + Part 2 协同）

四层递进防线，解决"System Prompt 单层约束不可靠"的问题：

| 层级 | 机制 | 作用 | 归属 |
|------|------|------|------|
| Layer 1 | Prompt 注入合规约束 | 预防（必要但不充分） | Part 2（Demo） |
| Layer 2 | 规则扫描（黑名单关键词、正则） | 拦截明显违规 | Part 1（监控平台） |
| Layer 3 | 独立合规判断 Agent（隔离上下文） | 深度合规审查 | Part 2（Demo） |
| Layer 4 | 高风险输出自动拦截 | 合规评分 < 40 分直接拦截 | Part 1（监控平台） |

**关键设计**：Layer 3 的合规判断 Agent 使用独立 LLM 调用上下文，不与业务 Agent 共享 Prompt，避免"自己审查自己"。Layer 2 和 Layer 4 作为平台层能力，不依赖具体 Demo 场景，可复用于任何领域。

**合规判断 Agent ≠ 风控评估 Agent**：前者判断"输出能否对外发布"（法规红线），后者判断"投资方案风险多大"（业务逻辑），两者在链路中处于不同位置。

## 6. Demo Agent 链路

```
                 ┌→ 技术面分析 ─┐
数据采集 ──→      │              ├→ 风控评估 → 综合决策 → 合规判断 → 最终输出
                 └→ 基本面分析 ─┘
```

6 个 Agent：数据采集 → 技术面分析 ∥ 基本面分析（并行）→ 风控评估 → 综合决策 → 合规判断

Demo 使用预置 Mock 股票数据（3-5 只），不依赖真实行情 API。6 个 Agent 中多数以 Prompt Engineering + LLM 调用为主，整体 Demo 开发量约 1-1.5 周，显著少于通用监控平台的开发量（3-4 周），核心价值是为监控平台提供可展示的被监控对象。

## 9. 关键创新点

1. **框架无关的通用监控模型**：通过适配器模式定义标准化 TraceRecord，不绑定特定 Agent 框架
2. **三层异常检测 + 五维质量评估**：从"对不对"到"好不好"的完整评价链路
3. **多层合规防线**：独立合规 Agent + 阻断机制，解决金融场景合规底线问题
4. **双通道优化反馈**：同时面向人类操作者和 Agent 自身，形成闭环改进
5. **并行链路可视化**：AntV G6 DAG 图实时展示并行 Agent 执行状态
