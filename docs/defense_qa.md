# defense_qa.md

基于真实实现准备的答辩追问（回答 30–60 秒）。

## 1. 为什么要用 Multi-Agent，不用一个 Agent？
一个 Agent 既要查数据、又要做技术面/基本面/风控/决策，prompt 会非常臃肿、容易顾此失彼。拆成七个 Agent 各司其职，每个 prompt 单一、可控，还能并行执行（技术面和基本面并行、三个决策并行），出了问题也更好定位到具体环节。这是"分工带来可控性和并行性"。

## 2. Agent 之间如何通信 / 共享状态？
靠 LangGraph 的共享状态字典（State）。每个 Agent 只往 state 里写自己的产出（比如技术面写 technical_report），下游 Agent 从 state 里读。这样 Agent 之间不直接耦合，改顺序只改图拓扑。

## 3. 怎么避免 Agent 无限执行 / 循环？
一方面图是固定拓扑、有明确的 END，没有动态循环条件；另一方面异常检测里有"循环检测"，对相同输入重复调用会告警。所以本项目不会无限执行。

## 4. 异常如何处理？
三层规则扫描：执行层抓超时/失败，行为层抓循环/缺失节点，输出层抓空输出。检测到就按 high/medium/low 分级告警，写进 anomaly_events 表，前端告警页展示。LLM 调用失败则降级兜底（回退默认分），不会让链路崩掉。

## 5. 监控机制怎么实现？
用 LangGraph 的 astream_events 事件流，通过一个零侵入的适配器，把每个 Agent 的起止时间、输入输出、耗时、token、父子关系采集成标准化的 TraceRecord。因为走的是框架原生事件，Demo 代码完全不用 import 监控代码。

## 6. Trace 保存在哪里？
PostgreSQL（Neon）。TraceRecord 落到 traces 表，异常、质量分、建议、指令分别落到各自的表，共 7 张表。前端通过 REST API 查询 + WebSocket 实时推送。

## 7. 为什么需要结果筛选？
LLM 是概率性系统，第一次生成的结果不一定最优。所以我让三个决策 Agent 并行产出候选，再走"异常过滤 → 质量排序 → 去重 → 推荐"选出最优，而不是只信一个答案。

## 8. Judge（评价者）会不会也判断错？
会。所以评价是"规则 + LLM 双保险"：规则能兜住确定性错误（如合规关键词、空输出），LLM 负责语义层面。但 LLM Judge 本身也有局限，我会如实说这是辅助评价，不是绝对正确，这也是为什么要有规则兜底。

## 9. 如何降低幻觉？
几个手段：数据采集用真实 yfinance 行情而非模型编造；质量评估里有"准确性"维度，LLM-as-Judge 专门查事实；合规层有敏感词库 + LLM 双重审查。但坦白说，这是原型，不能保证完全消除幻觉。

## 10. 多 Agent 的延迟和成本怎么处理？
延迟上，我把技术面/基本面、三个决策做成并行，质量评估的 LLM-as-Judge 也并行化了，单次从约 40 秒压到约 27 秒。成本上，规则层能快速过滤就不用 LLM，LLM 只用在语义评价。但整体延迟仍是瓶颈，因为 LLM 调用是主要开销。

## 11. 系统最大的瓶颈是什么？
LLM 调用延迟。七个 Agent 里大部分要串行调 LLM，这是时间大头。其次是多 Agent 的编排复杂度。所以下一步最想做的就是减少串行 LLM 调用、缓存中间结果。

## 12. 如果继续优化，下一步会做什么？
一是多轮对话的持久化（现在历史存前端，刷新就丢）；二是反馈指令的 LLM 动态生成（现在是预设模板，触发是智能的）；三是让 LLM-as-Judge 更细粒度、更准确。

## 13. 为什么这个项目适合证券场景？
证券业务有三个特点：分析链路长、合规要求严、结果要可追溯。这个项目正好对应——多 Agent 拆解长链路、敏感词库做合规拦截、全程 Trace 做可追溯。所以是能力层面的天然匹配。

## 14. 证券场景对可追溯性有什么特殊要求？
证券受强监管，一个投资建议为什么这么给，中间经过了哪些分析、有没有违规，都需要能回查。我的系统把每个 Agent 的输入输出、质量分、异常、拦截记录都持久化了，等于给"决策过程"留了完整的审计轨迹。

## 15. 零侵入是怎么做到的？
核心是"适配器 + 共享数据库"两层解耦。监控通过 LangGraph 的 astream_events 采集，Demo 不 import 监控代码；两者之间只通过共享数据库和一条 HTTP 反馈链路交互。所以换一个业务 Demo，监控平台一行都不用改。

## 16. 反馈闭环会不会失控（越改越差）？
设计上做了约束：指令按"目标 Agent + 维度"去重覆盖，不会无限堆积；有状态机（active/superseded），人随时能看、能删；而且指令只是追加进 prompt 的"改进提示"，不改核心逻辑。所以是"可控的自动优化"。

## 17. 敏感词库会不会误伤（比如正常表述里含敏感词）？
会有一点点风险，所以做了两个缓解：一是句级匹配（只有命中的那一句被标红/拦截，不影响整段）；二是敏感词本身可增删，发现误伤可以马上删掉。目前默认 10 个词都是典型违规表述，误伤概率较低。

## 18. 三个决策 Agent 有什么区别？
都是基于技术面+基本面+风控三份报告做决策，但 persona 不同：价值投资偏基本面（重估值/成长性）、趋势交易偏技术面（重趋势/买卖点）、综合决策是平衡视角。这样三个候选天然有差异，筛选才有意义。
