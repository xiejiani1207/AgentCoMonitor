# Slide 3 — 项目背景与核心问题

## PPT 中需要出现的文字

### 核心问题 1
标题：**多 Agent 协同，过程难掌控**
解释：复杂任务需要多个 Agent 各司其职，但各 Agent 的执行状态、输入输出、协作链路都成了"黑盒"，出了问题难以定位。

### 核心问题 2
标题：**执行过程缺监控**
解释：Agent 是概率性系统，可能超时、循环、输出空内容或违规，单靠人工 Review 成本高、时效差。

### 核心问题 3
标题：**结果质量无保证**
解释：LLM 输出质量参差，需要自动评价、筛选出更值得采用的结果，而不是直接相信第一次生成。

## 本页一句话核心结论
三个问题指向同一个方向：Agent 系统需要"可观测 + 可评价 + 可择优"。

## 事实依据
- `agent_monitor/core/anomaly.py`（三层异常扫描）
- `agent_monitor/core/quality.py`（五维质量评估）
- `agent_monitor/core/optimizer.py`（结果筛选优化）

## 我的口述稿（约 45 秒）
为什么做这个项目？现在多智能体系统很流行，但普遍有三个问题：一是 Agent 各司其职之后，整个协作过程变成了黑盒，谁先谁后、中间产出了什么都不清楚；二是执行过程缺乏监控，Agent 超时、报错、输出违规，都得靠人去翻日志；三是结果质量没有保证，模型第一次生成的答案不一定可信。所以这个项目就是围绕"可观测、可评价、可择优"三个词展开的。

**用户输入 → 投顾服务 → LangGraph 七 Agent 协同 → 零侵入采集 → 监控管线（采集/异常/质量/筛选）→ 结果输出 + 实时可视化**

**Agent** 名称：七个业务 Agent

## 事实依据

## 我的口述稿（约 70 秒）
这一页是整体架构。用户在前端提问，投顾服务接收后，交给 LangGraph 编排七个 Agent 协作执行——先数据采集，然后技术面和基本面并行分析，再风控，最后三个决策 Agent 并行给出不同策略的候选建议。整个过程通过一个零侵入的适配器实时采集每个 Agent 的执行记录，投进监控管线做异常检测、质量评估和结果筛选，最终采纳最优的候选，并把监控质检结果一起返回前端。这里我想强调两个设计点：一是 Demo 和监控是解耦的，监控通过适配器零侵入对接，换业务场景不用改监控代码；二是结果筛选面向的是三个候选决策，而不是流水线上的异构节点。

# Slide 5 — 智能监控机制

## PPT 中需要出现的文字

### 监控能力 1
标题：**执行状态采集**
正文：零侵入采集每个 Agent 的起止时间、输入输出、耗时、token、状态、父子关系，形成标准化 TraceRecord。
代码依据：`agent_monitor/adapters/langgraph.py`、`core/collector.py`

### 监控能力 2
标题：**三层异常检测**
正文：执行层（超时/失败）、行为层（循环/缺节点）、输出层（空输出），分高/中/低三级告警。
代码依据：`agent_monitor/core/anomaly.py`

### 监控能力 3
标题：**实时可视化 + 合规拦截**
正文：WebSocket 实时推送执行进度与告警；敏感词库句级检测，违规句标红、拦截并记录。
代码依据：`demo_service/main.py`、`core/sensitive_words.py`、`dashboard/src/pages/{Alerts,Topology}.tsx`

### 监控数据流
Agent 执行 → astream_events 采集 → TraceRecord → PostgreSQL → 异常/质量/筛选 → WebSocket → Dashboard

## 本页一句话核心结论
系统能回答三个问题：谁在跑、跑得对不对、结果能不能对外发布。

## 事实依据
- `agent_monitor/core/anomaly.py`（状态：pending/success/error/timeout；异常：timeout/loop/empty_output）
- `agent_monitor/core/sensitive_words.py`

## 我的口述稿（约 70 秒）
监控这一块，系统能回答三个问题。第一，"谁在跑"——每个 Agent 什么时候开始、什么时候结束、花了多久、输入输出是什么，都被采集成标准化的 TraceRecord 存进数据库。第二，"跑得对不对"——异常检测分三层：执行层抓超时和失败，行为层抓循环调用和缺失节点，输出层抓空输出。第三，"结果能不能发出去"——这块我重点做了合规检测：建了一个可增删的敏感词库，输出按句匹配，命中的句子标红、拦截，还会在告警页记一条"已拦截该说法"。整个过程通过 WebSocket 实时推到前端，你在 Dashboard 上能看到 Agent 一步步执行的状态和拓扑图。

# Slide 6 — 结果筛选优化

## PPT 中需要出现的文字

### 真实筛选流程
**候选结果 → 异常过滤 → 质量排序 → 去重 → 推荐**

### 评价维度
1. 合规性（权重 30%）
2. 准确性（25%）
3. 完整性（20%）
4. 相关性（15%）
5. 时效性（10%）

### 关键机制
- 候选来自三个并行决策 Agent（价值投资/趋势交易/综合决策）
- 两层评价：规则快速过滤 + LLM-as-Judge 语义打分
- 双通道建议：面向人类的建议 + 面向 Agent 的反馈指令
- 反馈闭环：不达标自动生成反馈指令，回灌进 Agent 提示词，下次执行自动优化

### 对应代码
`agent_monitor/core/optimizer.py`、`core/quality.py`、`core/feedback.py`、`demo_service/main.py`

### 当前 PPT 中不准确的表述
如 PPT 写"自研智能多维度动态结果优化算法"，请替换为：**规则约束 + 大模型语义评价**（实际是规则 + LLM-as-Judge，不是自研算法）。

## 本页一句话核心结论
多候选 + 规则与 LLM 双重评价 + 排序推荐 + 反馈闭环，构成结果质量控制。

## 事实依据
- `agent_monitor/core/optimizer.py`（rank 四步 Pipeline）、`core/quality.py`（五维权重）、`core/feedback.py`（反馈生成）

## 我的口述稿（约 70 秒）
结果筛选优化这一页，核心思路是"不要直接相信第一次生成"。具体做法是：三个决策 Agent 并行产出三个候选建议，然后走四步——先异常过滤，把有超时、报错、违规的候选剔除；再按质量分排序；再做相似度去重；最后标记推荐，最高的采纳、其次备选、其余存档。质量分怎么来的？两层：先用规则快速检查合规、完整、时效，再用 LLM-as-Judge 对准确性和相关性做语义打分，五维加权。这里我要强调诚实的一点：这不是什么自研的智能优化算法，就是规则约束加 LLM 评价的组合。更关键的其实是反馈闭环——如果某个 Agent 输出不达标，系统会自动生成一条反馈指令回灌进它的提示词，下次执行自动修正，全程不用人介入。

# Slide 7 — 证券公司应用场景

## PPT 中需要出现的文字

### 场景 1
标题：**投研辅助**
业务痛点：研究员需要整合行情、财务、技术指标等多源信息，分析链路长、耗时高。
项目能力：多 Agent 协同拆解分析任务，自动产出技术面/基本面/风控多份报告。
价值：把"多源信息 + 多步骤分析"自动化，研究员专注研判而非搬数据。

### 场景 2
标题：**投顾/客服辅助**
业务痛点：投资咨询需要多步骤查询、多知识调用，输出质量要求高、且必须合规。
项目能力：多轮对话 + 记忆 Agent 理解上下文；敏感词库句级检测 + 合规拦截。
价值：辅助生成高质量、可拦截违规表述的回答，降低合规风险。

### 场景 3
标题：**内部运营/风控辅助**
业务痛点：Agent 化的业务流程执行过程不可追踪，出了错难以审计定位。
项目能力：执行 Trace 全程采集、异常告警、链路拓扑可视化、结果可回溯。
价值：让流程"可观测、可审计"，异常可定位，结果可追责。

## 事实依据

## 我的口述稿（约 50 秒）
这套系统为什么适合证券场景？我觉得核心是三个点。第一，投研辅助——多 Agent 能把"查数据、技术分析、基本面分析、风控"这些步骤自动串起来。第二，投顾辅助——它支持多轮对话，还能用敏感词库做句级合规检测，命中违规就拦截，这对证券的合规要求很关键。第三，内部风控和审计——因为每一步执行都被记录了 Trace，出了错能定位、能回溯。当然我要强调，这目前是一个原型系统，还没有真正在生产环境落地，这些场景是能力层面的匹配，不是已经验证的业务收益。
