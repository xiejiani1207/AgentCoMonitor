## Slide 3｜项目背景与核心问题
**建议时长：45–50 秒**

接下来介绍一下为什么要做这个项目。

我在开发过程中发现，多智能体系统虽然能够通过分工解决更复杂的问题，但同时也带来了三个新的问题。

第一个是**协同过程难掌控**。当多个 Agent 串行或者并行工作之后，出了问题很难第一时间知道到底是哪一个 Agent 出了问题。

第二个是**执行过程缺少监控**。Agent 本质上还是概率性的系统，实际运行中可能出现超时、执行失败、空输出甚至不合规的内容，如果全部依赖人工去检查，成本会比较高。

第三个是**结果质量没有保证**。模型第一次生成的结果不一定就是最优结果，尤其当多个 Agent 都能给出不同建议时，还需要判断到底应该采用哪一个。

所以我把这个项目最终归纳成三个目标：

**让 Agent 的执行过程可观测，让输出质量可评价，让多个候选结果可以择优。**

---

## Slide 4｜整体技术架构
**建议时长：70–80 秒**

这一页是整个项目的整体架构。

为了验证监控系统，我实现了一个金融智能投顾 Demo。用户在前端输入问题以后，请求首先进入投顾服务，然后由 **LangGraph 的固定工作流**编排整个多 Agent 链路。

这里实际一共有 **7 个业务 Agent**。

首先由数据采集 Agent 获取数据，然后技术面和基本面两个 Agent **并行分析**；之后进入风控 Agent；最后再由价值投资、趋势交易和综合决策三个 Agent **并行生成三份不同视角的候选决策**。

这里我想重点强调的是下面这一层，也就是我的监控平台。

我没有让业务 Agent 主动去调用监控代码，而是通过一个**零侵入适配器**，利用 LangGraph 原生的事件流获取 Agent 的开始、结束、输入输出、耗时等信息，再统一转换成标准的 TraceRecord。

这些数据之后会进入监控管线，依次完成异常检测、质量评价和结果筛选，最后一方面选出更优的候选结果，另一方面把整个执行过程实时展示在前端。

所以整个系统可以概括成：

**七 Agent 协同执行，监控平台在旁边持续观察、评价和筛选。**

## Slide 5｜智能监控机制
**建议时长：65–75 秒**

这一页重点介绍监控部分。

我希望这套监控系统能够回答三个问题：

**谁在跑？跑得对不对？这个结果能不能对外输出？**

第一个问题是“谁在跑”。

系统通过 LangGraph 的 `astream_events` 获取执行事件，把每个 Agent 的开始时间、结束时间、输入输出、耗时、Token 和上下游关系统一记录成 TraceRecord，然后存进数据库。

第二个问题是“跑得对不对”。

这里我没有把它包装成一个复杂的智能算法，而是设计了比较确定的**三层规则检测**：执行层检查超时和失败，行为层检查循环调用和节点缺失，输出层检查空输出等问题。发现异常以后会按照严重程度产生告警。

第三个问题是“结果能不能发出去”。

因为项目使用金融场景做验证，所以我还增加了**合规检测**。系统维护一个可动态增删的敏感词库，对输出进行句级检查，发现违规表述以后可以标红、拦截并记录。

这些状态通过 WebSocket 实时推送到 Dashboard，所以用户能够直接看到整个 Agent 链路当前运行到了哪里。

## Slide 6｜结果筛选优化
**建议时长：70–80 秒**

有了监控以后，下一步的问题就是：

**Agent 成功运行结束，并不代表它的结果一定足够好。**

所以我进一步设计了结果质量评价和筛选机制。

前面提到，最后有三个不同角色的决策 Agent，它们会分别从价值投资、趋势交易和综合视角给出候选结果。

系统不会直接随机选择其中一个，而是经过四个步骤：

**异常过滤、质量排序、相似去重，最后给出推荐。**

质量评价采用的是**规则和 LLM-as-Judge 相结合**的方式。

一共从五个维度评价：合规性、准确性、完整性、相关性和时效性。

比较确定的问题，比如违规表达、内容缺失，可以优先通过规则判断；而准确性和相关性这种更偏语义的问题，再交给大模型进行辅助评价。

这样做主要是因为纯规则速度快、可控，但是不擅长语义判断；如果全部交给大模型，又会增加延迟和成本，所以我选择了两者结合。

另外还有一个我觉得比较重要的设计，就是**反馈闭环**。

如果系统发现某个 Agent 在某个维度持续表现不好，可以生成对应的改进指令，回灌到这个 Agent 后续的 Prompt 中，让下一次执行进行针对性调整。

所以这里不仅仅是“发现结果不好”，而是希望进一步做到：

**发现问题、筛选结果，再把问题反馈回执行端。**

## Slide 7｜证券公司应用场景
**建议时长：50–60 秒**

从证券公司的应用场景来看，我认为这套能力主要有三个比较直接的方向。

第一个是**投研辅助**。研究过程中经常需要同时处理行情、基本面、技术指标和风险等多类信息，这种长链路任务比较适合通过多个 Agent 分工处理。

第二个是**投顾或者客服辅助**。这一类场景除了回答问题以外，对输出质量和合规性要求也比较高，所以监控、质量评价以及敏感内容拦截都会比较重要。

第三个是**内部运营和风控辅助**。随着 Agent 参与的业务流程越来越复杂，仅仅知道最终结果是不够的，还需要知道中间执行了什么、哪里发生异常，以及最后为什么得到这个结果。

所以我认为这个项目和证券业务比较契合的三个关键词是：

**可追溯、合规、质量可控。**

当然，目前这个项目还是一个**原型系统**，这里介绍的是能力层面的应用匹配，并不是说已经在真实生产业务中落地。

## Slide 8｜项目实机展示
**建议时长：50–60 秒**

接下来我用一个实际 Demo 简单展示一下整个流程。

这里我输入的是“**分析 600519 贵州茅台**”。

大家可以看到，请求发出以后，下面的 Agent 会按照工作流逐步执行，其中技术面和基本面是并行的，最后三个不同策略的决策 Agent 也会并行生成候选结果。

执行完成以后，除了最终回答之外，还可以看到每个 Agent 的执行记录和质量评价。

这里重点看结果筛选部分，三个候选决策会根据前面介绍的评价机制进行排序，系统最终选择质量更高的结果。

另外，在演示模式下如果人为注入一条不合规表达，可以看到对应句子会被检测并拦截，同时在监控侧产生告警，并生成针对 Agent 的反馈指令。

所以这一段 Demo 实际上把前面讲的四件事串了起来：

**多 Agent 协同、执行监控、结果筛选以及合规控制。**

## Slide 9｜实习收获与企业文化认识
**建议时长：70–80 秒**

最后简单总结一下这次实习对我个人的影响。

第一个变化是**工作方式**。

以前面对一个新技术，我比较容易产生“先把它完整学会再开始做”的想法。但这次项目让我逐渐习惯先围绕实际问题做一个最小验证，先把链路跑通，再逐步增加监控、质量评价、结果筛选和反馈闭环。

第二个变化是**学习方式**。

比如开发 LangGraph 监控适配器的时候，我遇到过框架版本变化导致旧的回调方式拿不到需要的信息。后来不是继续盲目修改，而是从问题本身出发去查文档、Issue，甚至直接阅读相关源码，最后切换到 `astream_events` 解决问题。

第三个是**团队协作和工程意识**。

这个项目里我越来越意识到，清晰的接口边界其实也是一种沟通方式。比如为了做到低侵入，我把业务 Demo 和监控平台解耦，两边通过适配器、数据库以及服务接口交互。边界明确以后，不论是开发、调试还是后续替换业务场景都会更加清楚。

通过这次实习，我最大的变化可以总结成一句话：

**从关注“代码能不能跑”，逐渐转向思考“问题怎么拆、边界怎么定、系统怎么持续迭代”。**
